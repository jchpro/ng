Overview

Data tables for list views, the usual admin-app case: rows from an API with a search, filters, sorting and paging. The rows are a plain <table class="kit-table"> with an @for in your own template, so every cell is typed and there is no column definition to learn. The kit supplies the look, the frame around it (kit-data-table: toolbar, loading, empty and error states), the sortable header and the paginator.

The search, filters, sort and page are the signals of a kitTableState(), which also builds the params of the request. Give it to the frame and the parts inside bind themselves; what you load and how you map params to your API stays yours.

Usage

Put the table inside kit-data-table and fill the slots you need, each marked by an attribute: kitTableSearch and kitTableFilters on the left of the toolbar, kitTableActions on the right, kitTableChips for the applied filters. A kit-paginator goes to the footer on its own. Every part is optional, and a toolbar with nothing in it is not drawn.

State

kitTableState() holds the search, filters, sort and page as signals, and params, everything a request depends on. Anything that narrows or reorders the rows (search, a filter, the sort, the page size) sends the table back to page 1. Build the request from params in a resource() or httpResource(), which reloads by itself:

kitPagedList(state, loader) does the loading for a server that pages: the loader is called with params whenever the state changes and answers { items, total }, which fits any API. It gives back the resource for the frame and the rows, total and empty signals; rows keeps the previous page while the next one loads, and after a load fails (the error state covers it). After a delete, reloadAfterRemoval() loads the page again, or the one before it when the removed row was the only one of the last page.

Handed to kit-data-table [state], the parts inside bind to it: input[kitSearch] (typing is debounced into state.query, Enter applies it at once), [kitFilter="name"] on a native select, th[kitSort] and kit-paginator (its total comes from the frame's [total]). [resource] makes the frame follow the resource's loading and error, and "Try again" reloads it. Without a state every part still works on its own bindings.

urlSync (opt-in) keeps the state in the query string: ?q=ada&sort=-seats&page=2&role=Admin. Values equal to the starting state are left out, a reload or a shared link restores the view, and a navigation from outside is applied to the state. By default it uses replaceUrl, so typing and paging don't fill the history; history: 'push' makes a change of the page, sort, filters or page size a history entry, so the back button steps through them (typing in the search still replaces the entry). { prefix: 'users.' } namespaces the names for a second table on the same route.

Why not column templates

Material-style tables define each cell in an <ng-template>, whose context Angular can't type without a guard directive that is told the row type. With a plain @for the row variable is typed for free. Always track by a stable id: a re-sort then moves the existing rows instead of rebuilding them. A page of 25 to 100 rows costs nothing either way, and server paging means you never render more.

Selection, filters, columns, density

The rest of an admin list, each piece optional and bound by the same frame. All of them are in the demo above.

Selection and bulk actions

kitTableSelection(key, { state }) keeps the selected rows by their key, so a selection survives paging and sorting. The checkboxes are plain kit-check__inputs bound by hand (isSelected, toggle, and allSelected / someSelected / toggleAll for the header), which keeps the row type. Give it to the frame as [selection] and, while rows are selected, the toolbar gives way to a bar with the count, your kitTableBulk actions and "Clear selection"; add kit-table__row--selected to the selected rows. With a state the selection empties when the search or a filter changes, so a bulk action never reaches rows the person can no longer see.

Applied filters as chips

<kit-filter-chips kitTableChips [labels]="{ role: 'Role' }" /> draws a chip for each applied filter (the name from labels, the value as stored, or through [formatValue]), each removing its filter, and a "Clear all". It draws nothing while no filter is applied. The search text isn't a filter and gets no chip.

More filters than fit

Up to three simple filters sit inline as selects. Beyond that, <kit-filter-panel> puts them behind a "Filters" button that shows how many are applied; [filters] names the ones inside it, so inline filters aren't counted or reset with them. It is built on <kit-popover>, a button that opens any content in an overlay and stays open while you use it (Escape or a click outside closes it).

Columns and density

kitTableColumns() lists the columns the person may hide. Mark each header and its cells with kitCol="id", pass it as [columns] and add <kit-column-picker />; a locked column can't be hidden and storageKey remembers the choice in the browser. <kit-density-toggle /> switches the frame's [(density)] between default and compact rows; densityStorageKey on the frame remembers it in the browser.

Row expansion

A detail row is an ordinary <tr> you render under the row while it is open, so it has the row's type and can hold anything. kitTableExpansion(key, { single, state }) holds which rows are open; <kit-expand-toggle> is the button (aria-expanded, a name that includes the row); <td kitDetail> spans every column that is shown, also as columns are hidden. With a state everything collapses when the page, sort, search or filters change.

Data in memory

kitClientTable(rows, state, options) filters, sorts and pages a list you already have by the same state, for a table without a server: view.rows() and view.total(). This demo's "API" is applyKitTableParams(), the same logic as a plain function. Search matches every word, ignoring case and accents; sorting handles numbers, dates, booleans and natural-order text, with empty values last.

Sorting

<th kitSort="name"> turns the header label into a button and sets aria-sort. A click sorts ascending, then descending; add cycle for a third click that clears the sort. The choice lands in the state's sort ({ field, direction }; the frame's own [(sort)] model without a state), which is what your API's sort parameter is built from. One column at a time.

Column conventions

Modifier classes go on the <th> and its <td>s alike, so a header lines up with its column.

Data Convention
Identity (name, title) kit-table__link on the link that opens the row, and kit-table__secondary for the second line. The link is the way into the row; the row itself is not clickable
Text Left-aligned. kit-cell--truncate cuts it with an ellipsis (width from --kit-cell-max-width), add a title with the full text
Numbers kit-cell--num: right-aligned, tabular figures, the header too
Dates kit-cell--nowrap, with the time (or relative part) in kit-cell--muted. Format in the app, the kit has no date logic
Status, category kit-badge with --success, --warning, --danger or --info (a colored dot before the text); plain is neutral
Yes / no kit-table__bool: an icon and a word, never color alone. --off mutes the "no"
IDs, codes kit-cell--mono, usually with kit-cell--muted
No value kit-table__empty, an em dash with role="img" and an aria-label
Row actions Last column, kit-cell--actions. One icon button that opens a menu (or at most one inline action next to it), always with an aria-label that names the row

Row height is kit-table--compact for dense lists. Set --kit-data-table-max-height on the frame for a table that scrolls under its sticky header.
